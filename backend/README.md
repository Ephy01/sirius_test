# Sirius Gate API

Вертикальный срез серверного ядра: контесты, участники, персональные коды
доступа, попытки, воспроизводимые экземпляры смешанного набора семейств,
адаптивный режиссёр и журнал событий.

## Локальный запуск

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -e '.[test]'
.venv/bin/uvicorn app.main:app --reload --port 8001
```

Swagger UI: <http://127.0.0.1:8001/docs>.

По умолчанию используется `sqlite:///./sirius_gate.db`. Для PostgreSQL
передайте `DATABASE_URL=postgresql+psycopg://user:password@host/database`.
Перед публикацией необходимо заменить `SECURITY_SECRET` и
`CODE_HMAC_SECRET`.

## Поток доступа

1. Организатор обменивает `ORGANIZER_CODE` на Bearer-токен.
2. Создаёт контест и регистрации участников.
3. Генерирует персональные коды `SG-XXXX-XXXX`. Открытый код возвращается
   только в ответе генерации; в базе хранится HMAC-SHA256.
4. Публикует контест.
5. Участник обменивает персональный код на Bearer-токен.
6. Получает контекст и запускает попытку. Повторный запрос запуска возвращает
   ту же активную попытку.
7. Получает текущую задачу, отправляет ответ, выполняет пошаговые
   интеракции в интерактивных семействах (пробы Zendo, операции машин)
   или пропускает задачу и запрашивает следующую. Одновременно активна
   не более чем одна задача.
8. После завершения попытки организатор может отдельно перевыпустить код или
   выдать одноразовое разрешение на новую попытку. Разрешение не создаёт
   попытку и не запускает таймер: участник запускает её самостоятельно.

Роль подписана сервером внутри HMAC-токена и не определяется клиентом по
формату кода.

Каждый экземпляр задачи сохраняет версию генератора и seed, производный от
seed попытки, номера задачи, семейства и версии генератора. Семейство
выбирается воспроизводимо с учётом весов в `task_config`.

Новые контесты записывают `environment_key=mixed` и используют
`director-v2`. Режиссёр фиксирует snapshot `task_config`
при старте попытки, сначала покрывает все включённые семейства,
не допускает два задания одного семейства подряд при наличии альтернатив и
затем балансирует маршрут по весам и дефициту показов. Ошибка влияет на
следующее появление семейства, но не вызывает его немедленного повтора.
Сложность каждого семейства вычисляется независимо по окну из трёх результатов
и может как повышаться, так и понижаться. Контесты без
`trajectory.mode=adaptive` сохраняют старый маршрут
`weighted-family-route-v1`. Старые строки `chess-world-director-v1` и
`geometry-world-director-v1` обслуживаются совместимыми shim-модулями.

В новых контестах `chess_coverage` предлагает выбрать подмножество шахматных
фигур на отмеченных клетках, покрыть все цели и минимизировать суммарный вес.
Генератор перебирает все подмножества кандидатов и принимает только варианты с
единственным оптимумом. Интеракции выбора и `reset` идемпотентны.

Dice & Chess сохранён как совместимый тип и имеет два последовательных типа
заданий, оба с доской:

- уровни 1–2 — вероятность того, что тип фигуры на кубике представлен на
  доске или в заданной области;
- уровень 3 и выше — вероятность события в легальной шахматной позиции после
  броска одного кубика фигур: наличие легального хода, взятия или хода с шахом.

Позиции воспроизводимо получаются легальными ходами из стандартной начальной
расстановки и проверяются `python-chess`. Права рокировки и взятия на проходе
сбрасываются, поэтому публичных данных — доски и стороны хода — достаточно для
независимого восстановления множества легальных ходов.

Вероятность вычисляется полным перебором конечного пространства исходов и
хранится как точная сокращённая дробь. Ответ можно передать дробью, десятичным
числом с точкой или запятой либо в процентах. Новые задания используют версию
`dice-chess-world-v3`; проверка уже сохранённых заданий
`dice-chess-mission-v2` и `dice-chess-probability-v1` остаются доступными.

Chess960 использует версию `chess960-mission-v2`: проверку допустимости на
первом уровне, поиск исправляющей перестановки на уровнях 2–4 и подсчёт всех
исправляющих перестановок на уровне 5 и выше. Все 28 неупорядоченных пар полей
перебираются сервером. Проверка сохранённых задач
`chess960-validation-v1` остаётся доступной.

Micro-Penultima использует одну нейтральную фигуру, статические препятствия и
скрытое правило из генерируемого пространства симметричных векторов. Генератор
строит симметричный граф ходов и проверяет цель поиском в ширину, поэтому после
любого принятого хода цель остаётся достижимой. Внутри трёх задач одной главы
сохраняются правило, препятствия и фактическая конечная клетка. Следующая цель
ветвится по истории: уверенное решение усложняет маршрут, шумное закрепляет
правило, а пропуск создаёт короткую восстановительную цель. Ходы идемпотентны
по `client_action_id` и полностью записываются в журнал. Версия
`micro-penultima-v1` остаётся доступной для сохранённых задач.

Старые контесты Geometry World используют `geometry-atlas-v1` и четыре
семейства с общим контрактом сцены из точек и рёбер:

- `geo_zendo` — скрытый геометрический предикат, примеры, две пробы оракула и
  классификация целевых карточек;
- `geo_transform` — распознавание одного из точных преобразований группы
  \(D_4\);
- `geo_probability` — точная вероятность события на индивидуальном графе;
- `geo_graph` — добавление или удаление ребра с формальной проверкой
  связности и ацикличности.

Для Geometry World seed дополнительно изолирован пространством имён мира.
Проверка Zendo-проб идемпотентна по `client_action_id`; скрытое правило,
ответы целей и точная вероятность никогда не попадают в публичное состояние.

В смешанных контестах `geo_zendo` использует `geometry-zendo-v2` и
`graph-dsl-v1`: правило выбирается из детерминированного пространства
графовых предикатов после фильтрации по базовой частоте и MDL-сложности.
Участник видит два положительных и два отрицательных примера, может сделать до
пяти проб и классифицирует восемь near-miss целей. Для каждой пробы сервер
фиксирует размер пространства версий до и после ответа, фактический прирост
информации и лучший доступный прирост; индекс правила, маски и ответы остаются
только в закрытом состоянии задачи.

`machine_reach` объединяет четыре точных генератора: `lamps_gf2`,
`numeric_machine`, `perm_puzzle` и `leaper_board`. Общие интеракции —
`apply_op` и `undo`; финальные ответы — `done` и `impossible`. Для достижимых
экземпляров хранится кратчайший witness, для недостижимых — проверяемый
сертификат инварианта. Ложное «недостижимо» не закрывает задачу и блокирует
ввод на 15 секунд.

Для `lamps_gf2` длина кратчайшего решения насыщается пятью шагами: при
заданных ТЗ 3–5 коммутирующих инволютивных кнопках любая последовательность
сокращается до нажатия каждой кнопки не более одного раза. Диапазон 8–12 для
этого подтипа математически потребовал бы не менее 8 кнопок либо отказа от
модели GF(2); остальные подтипы используют полный диапазон сложности.

`nim_like` — одноходовые normal/misère игры с кучами. Генератор поддерживает
соотношение 60/40 выигрышных и проигрышных позиций, а сервер вычисляет точный
выигрышный ход и `regret`.

Для новой конфигурации источником истины служит `task_config.families`:

```json
{
  "trajectory": {"mode": "adaptive", "director_version": "director-v2"},
  "cohort_seed": "optional-wave-seed",
  "families": [
    {"family": "geo_zendo", "skin": "graph", "weight": 25},
    {
      "family": "machine_reach",
      "skin": "machine_panel",
      "weight": 25,
      "sub_kinds": ["lamps_gf2", "leaper_board"]
    },
    {"family": "nim_like", "skin": "counters", "weight": 20},
    {"family": "penultima", "skin": "chess", "locked_chapter": true}
  ]
}
```

Скин не влияет на seed. При наличии `cohort_seed` попытки одного номера во
всей волне получают один seed. Каждое новое событие оценивания содержит
`continuous_score`, `difficulty`, `family` и `generator_version`.

Публичный API не возвращает seed, `private_state`, ответ участника или результат
проверки. Контекст участника также не содержит `task_config` и
`cohort_seed`: полная конфигурация контеста доступна только организатору.

Хронология хранится в `attempt_events` как последовательность вставляемых
событий с монотонным номером внутри попытки. Официальная проверка ответа
выполняется обычным кодом и не зависит от LLM. Браузер отправляет только
семантические события интерфейса: показ задачи, команду, вставку текста,
копирование, фокус и видимость вкладки. Нажатия отдельных клавиш и движения
мыши не собираются. Идемпотентность обеспечивается отдельной таблицей
`client_telemetry_receipts`; на одну попытку принимается не более 5000
клиентских событий и не более 240 событий в минуту.

Клиент прикрепляет событие к конкретной попытке и повторяет неуспешную
доставку с тем же ID. Для событий, созданных до окончания попытки, действует
пятиминутное окно доставки после дедлайна с проверкой клиентской отметки
времени и длительности сессии. Это окно относится только к телеметрии:
ответы, ходы и остальные игровые команды по-прежнему требуют активную попытку.

Организатор получает журнал участника в UTF-8 `.txt`. Экспорт строится по
запросу из `attempt_events` и показывает для каждого события UTC-время,
интервал от начала попытки, интервал от предыдущего события и интервал от
создания связанной задачи. Закрытые состояния генераторов, seed, токены и коды
доступа в файл не включаются. Публичное условие и видимое состояние задачи
сохраняются, чтобы ответы можно было интерпретировать без доступа к закрытому
состоянию генератора.

## API

Все маршруты имеют префикс `/api/v1`.

| Метод | Маршрут | Доступ |
|---|---|---|
| `GET` | `/health` | публичный |
| `POST` | `/access/redeem` | публичный |
| `GET`, `POST` | `/contests` | организатор |
| `DELETE` | `/contests/{id}` | организатор |
| `GET`, `POST` | `/contests/{id}/enrollments` | организатор |
| `POST` | `/contests/{id}/codes` | организатор |
| `POST` | `/contests/{id}/enrollments/{enrollment_id}/codes/rotate` | организатор |
| `POST` | `/contests/{id}/enrollments/{enrollment_id}/attempts/grant` | организатор |
| `GET` | `/contests/{id}/enrollments/{enrollment_id}/telemetry` | организатор |
| `POST` | `/contests/{id}/publish` | организатор |
| `GET` | `/participant/context` | участник |
| `POST` | `/participant/attempts/start` | участник |
| `POST` | `/participant/telemetry` | участник |
| `GET` | `/participant/tasks/current` | участник |
| `POST` | `/participant/tasks/next` | участник |
| `POST` | `/participant/tasks/{id}/answer` | участник |
| `POST` | `/participant/tasks/{id}/interactions` | участник |
| `POST` | `/participant/tasks/{id}/skip` | участник |
